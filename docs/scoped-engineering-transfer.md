# 常驻工程服务与程序／硬件分开传输

## 使用

1. 重开工程站，在“连接与工具”点击“连接工程服务（免 SSH）”。当前电脑与 `192.168.1.31` 已完成一次配对；其他电脑先点“首次配对工程服务”。配对凭据保存在 Windows 凭据管理器，不写入工程和配置 JSON。
2. 点击“编译”一次完成工程检查、ST 编译和候选包生成。F7 同样执行。顶部“下载程序”也会先重新构建，再上传和进行目标 Linux 编译。
3. 左侧选程序、函数、功能块、类型、全局变量、任务或路径时，顶部显示“上传程序／下载程序”；选硬件、从站、IO、轴或网络时显示“上传硬件／下载硬件”。

“上传”固定表示 **PLC → 工程站**，“下载”表示 **工程站 → PLC**。程序范围是完整 PLC 应用及其依赖，不将一个函数块独立当作可运行应用。

## 在线

独立普通用户服务监听 `https://192.168.1.31:18445`，不依赖 PLC 或运动核心的生命周期。日常连接使用已配对的证书和设备授权；工程站不会在未连接时自动回退 SSH。旧设备的 SSH 兼容连接需明确选择。

在线从设备取得实际活动程序的源身份和权威调试映射，核验源码、符号、目标配置、真实 MD5 及变量布局后监视；不要求先在本地生成候选包。每次采样继续检查实际程序 MD5。工程或设备变化会使旧数据和写权限失效。BOOL 修改仍是带确认和身份核验的单次写入。

首次配对用现有可信 SSH 通道读取授权，此后无需反复 SSH。配对过期或设备证书替换时明确重新配对，不绕过证书验证、不重试未知写操作。Runtime 重启可能断开调试，但工程服务仍在，可重新连接并核验。

## 程序传输

- 上传读取实际活动版本，验证库、库存、调试映射及源工程归档。先显示设备和内容摘要，保存为独立 `.stproj`，再决定是否打开；当前未保存内容不会静默覆盖。
- 新候选包包含库存摘要覆盖的 `engineering-archive.json`，保存原始 ST、对象、任务及还原所需元数据。
- **旧版本没有源工程归档时无法保证还原 ST。** 当前现场活动版本属于这种情况，会明确提示“该版本未保存源工程，无法还原 ST”。不会将生成的 C++ 假装成 ST。新版下载的版本才支持完整程序回读。
- 下载程序先构建，再检查设备组态。物理总线、IO、轴映射、限值或周期不一致时拒绝程序切换，提示先“下载硬件”；不自动改组态、不停止原程序。组态一致才进入 Runtime 重启确认，成功后保持原运行／停止状态。

## 硬件传输

- 上传验证实际加载的物理指纹、反馈与轴清单，再读回对应已保存的组态。确认一次后，直接替换当前工程中的硬件、网络描述、轴控周期和通信配置，刷新页面并标记未保存；使用工程的“保存”即可持久化，不要求另存 JSON。保留 ST 源程序，不修改设备。取消、组态无效或确认期间工程/目标变化时保持原组态。
- 下载使用独立硬件包，**不依赖 ST 编译通过**，也不激活 PLC 程序。轴必须已停稳且撤使能。确认后停止 PLC（如原来运行）并重启运动核心，验证实际组态和轴服务；完成后 PLC 保持停止。
- 更新后旧程序不匹配新硬件或轴映射时禁止启动。结果不明时停止后续操作，先查实际状态，不自动重试或使能轴。

## 重启后的核心恢复

`stworkbench-ethercat-restore.service` 在开机时校验并恢复上次由 root 保存的物理组态，再允许工程用户服务启动。它校验固定核心程序、总线指纹、机械和 IO 文件摘要，不使用用户工程中的任意启动参数，不启动 PLC 或使能轴。已有核心运行时不替换它；未保存组态时不自动创建组态。

硬件应用仍使用受限代理创建核心实例。核心临时服务在重启后消失属于已确认的未启动状态，协调器允许在 PLC 停止后进入原有初始化流程；无法确认的服务状态仍拒绝下载。轴桥接增加启动失败重试，已进入运行后的通道故障不自动重放轴命令。

首次安装开机恢复使用 `linux/ethercat-i210/install-boot-restore.sh`，只授权固定的恢复程序和服务，不增加 sudoers 权限。现场已安装启用；未进行整机重启测试。

2026-10-22 现场验证：相同物理组态的硬件包应用成功，随后硬件回读成功；PLC 维持停止、活动程序未替换、轴保持 Disabled，核心接受的轴命令序号为 0。核心缺失、服务状态不明或轴桥接未就绪时，工程服务显示对应中文原因，不再只返回统一英文提示。

现场已安装普通用户 `stworkbench-engineering.service`，并启用用户 lingering，退出登录后仍常驻。依赖使用独立虚拟环境，未修改 OpenPLC Runtime 的环境。设备部署代码在 `/home/a/st-workbench-deployment`，状态与候选在 Runtime 的 `deployment` 数据目录，二者分开。

Linux 上通过 25 项工程服务测试和 99 项部署测试。桌面回归覆盖范围切换、一键产包、ST 失败时独立硬件下载、取消、身份变化、组态不一致阻断，以及无本地候选时的 BOOL 确认。解决方案构建及部署、MCP、编译器回归结果见 `artifacts/scoped-*.log`。

实机只读验证已完成首次配对、使用已存凭据再次连接、HTTPS 状态、活动调试映射、WebSocket 读取以及硬件回读。现场旧程序无源归档，因此没有将它宣称为成功完整上传；本地未找到同源工程，本轮也未宣称完成其完整编辑器在线绑定。记录在 `artifacts/scoped-engineering-device-verification.json`。验证未下载/激活程序、启停 PLC、写变量或移动电机。
