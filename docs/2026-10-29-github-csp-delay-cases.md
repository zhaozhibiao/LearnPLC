# GitHub CSP 时序与跟随误差案例复查（2026-10-29）

本轮仅研究第一方仓库、issue讨论和源码，未复位、使能或运动设备。现场仍保持前轮保护退出状态。不把相似案例当作本机根因已经证实。

## 1. LinuxCNC EtherCAT：周期失步的实际结案案例

源：https://github.com/sittner/linuxcnc-ethercat/issues/45

2018年报告CSP匀速时运动不均匀、帧间隔偏差大。维护者提供修订后的参考钟同步、主站周期向参考钟同步两种策略，并限制PLL调节幅度，要求检查实时抖动和PLL误差。维护者报告多种驱动/PC测试，报告者随后确认在Hiwin及Beckhoff硬件可工作。不是一次改参数立刻成功，而是时钟闭环、实时环境与测量一起处理；不能把该旧分支配置直接套到现代版本。

当代文档：https://github.com/linuxcnc-ethercat/linuxcnc-ethercat/blob/master/documentation/distributed-clocks.md

文档区分参考钟跟主站R2M与主站周期跟参考钟M2R；对其已测试的DC伺服推荐后者，提供PLL误差、修正量和重置计数。DC从站间同步良好，不等于主站线程相位已同步。两种方向都存在，不应仅看到当前使用R2M便判定代码错误。

补充原始报告：https://github.com/LinuxCNC/linuxcnc/issues/3564 。描述主站和DC运行速率不一致时，驱动可能一周期没收到新目标、下一周期又收到跨周期增量，出现瞬时加速度/转矩尖峰。该issue正文是报告者分析，不能当成本机抓包结论。

## 2. ECMC：明确建模输入延迟

发布说明：https://github.com/epics-modules/ecmc/blob/master/RELEASE.md
源码：https://github.com/epics-modules/ecmc/blob/master/devEcmcSup/motion/ecmcEncoder.cpp

该项目提供SetAxisEncDelayCyclesAndEnable，可按编码器显式设置包含小数周期的延迟，缺省关闭。源码将未补偿位置用于速度估计，随后再做补偿，避免把补偿结果反馈到速度估计；并处理量化、有效状态及幅度限制。发布说明也记录过补偿稳定性修复。因此不能将“有延迟补偿功能”理解为可以任意平移反馈，或原样复制某版计算式就安全。

对本项目的意义：需要配置可追踪的时延模型，而不是永远只认上一帧目标。必须先验证延迟稳定性，并保留原始目标/反馈、驱动60F4及原始保护观测。延迟模型失效、WKC无效或时序异常应判异常；不能靠增大补偿值把真实滞后抵消。

## 3. 同型号IS620N：SOEM #501

源：https://github.com/OpenEtherCATsociety/SOEM/issues/501

同为Inovance IS620N，报告Er.E08。讨论中抓包发现约1.855ms及0.140ms的相邻帧间隔，推翻了只看平均周期/程序打印便判断时序正常的做法。维护者要求完整初始化和正确配置同步。报告者最后确认在其SOEM版本中调整DC/SYNC0及映射初始化顺序后可运行。其使用SOEM，当前工程使用IgH，两者接口和初始化语义不能直接互换。

这个案例针对E08，与本次总线仍OP且603F=0、主站软件跟随保护触发不是同一故障。可借鉴真实帧时刻和同步参数读回的诊断方法，不能声称它已证明本机E08或跟随误差的唯一根因。

## 4. 第一方台架工程：主站误差与驱动误差分开记录

源：https://github.com/jayem1427/lemontart_lcnc_config/blob/main/docs/A6_TUNING.md

该工程作者将LinuxCNC跟随误差与驱动60F4分开采集，还记录了启动SDO覆盖台架整定值的问题。它是项目作者的工程实践，不能视为驱动厂家规范，也不采用其扩大故障窗口的试验参数。

## 对本机300rpm失败的判断

本机峰值帧已发送目标2655909、驱动内部需求2645905、实际2646160counts。主站比较得到9749counts误差(0.009297rev)，而同帧60F4为383counts；内部需求与实际相差-255counts，两个驱动内部对象并不保证同一内部采样时刻。加速后段历史匹配在约3周期时残差最小，但并非精确固定3ms。

这些证据使“主站发布/驱动应用/反馈采样的时刻归属”成为优先假设；仍不足以排除加速抖动、驱动内部插补或真实闭环滞后。

## 下一步应采用的顺序

1. 未使能时读回0x1C32/0x1C33同步类型、周期及支持的时序/丢失计数；记录实际IgH/网卡/内核版本与参考钟选择。
2. 增加每周期收、发时间与参考钟相位观测，检查SYNC0前PDO送达裕量和尾部抖动。必要时抓真实帧；不能只看计划1ms和WKC。
3. 确定适合该现场的R2M或M2R闭环和SYNC0相位，先验证数据是否稳定按周期消费。
4. 若仍有稳定处理延迟，再设计有上限、显式配置并有异常检测的时间对齐/补偿；原始误差、对齐误差及60F4都保留，分别定义保护语义。不能直接填3ms或只提高误差阈值。
5. 离线注入漏周期、迟到、速度突变和真实失跟，证明保护仍有效，再从低速到300rpm复验。300rpm通过前不执行3000rpm或工程站迁移。

本轮找到了可借鉴的真实修复案例与显式延迟建模实现；没有找到可直接证明本机根因的同版本IS620N+IgH现成补丁。

## 交付相位与数量级核对

LinuxCNC EtherCAT当前DC文档在Process-data Sync Units一节明确说明SYNC0相位偏移必须覆盖对应帧发送延迟，才能在紧随其后的SYNC0锁存输出。该节多速率架构不等于本机实现，但“输出应在消费时刻前送达”的时间预算仍需核实。

本机绝对睡眠后接收、计算、发送，当前sync0Shift=0；需要测真实参考钟相位和驱动应用时刻，不能只凭shift=0判错，也不能无依据改成半周期便声称修复。

峰值帧附近速度约3.2rev/s，若比较链存在3ms时差，误差项约0.0096rev，与实测0.009297rev接近。这是数量级验证假设，不证明时差固定3ms，不能据此自动修改保护。
