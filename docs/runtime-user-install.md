## Reviewable files and commands

The destination is `/home/a/.local/share/st-workbench/runtime-v4.3.0`; installation requires explicit `--resume` for an existing destination. `linux/runtime-install/install-user.sh` performs preparation only. `isolate.py` validates every expected upstream edit before changing any file, relocates three native socket/watchdog paths and the webserver socket paths, selects an absolute private executable path, disables EtherDOG and LAN discovery, binds HTTPS to `127.0.0.1:8443`, and passes `--safe-mode` on native daemon startup/restart. It preserves the underlying scheduler and compiler implementation. Changes are recorded as `isolation.patch` next to the pinned revision and dependency lock. `run-user.sh` refuses any pre-existing program library before launching, preventing an unreviewed program from being loaded when the service starts.

After copying the whole `linux/runtime-install` directory to `/home/a/st-workbench-runtime-install`, execute as `a`:

systemctl --user status stworkbench-openplc.service --no-pager

## Program-package and activation blockers

At this pinned revision, [compile.sh](https://github.com/Autonomy-Logic/openplc-runtime/blob/a9e38d901fb87deb5a8cf778b52639b9387834d0/scripts/compile.sh) requires `core/generated/generated.hpp`, at least one generated `.cpp`, uploaded `strucpp_runtime/include`, and the Runtime-supplied `core/strucpp_runtime/runtime_v4_entry.cpp`. [Makefile.strucpp](https://github.com/Autonomy-Logic/openplc-runtime/blob/a9e38d901fb87deb5a8cf778b52639b9387834d0/scripts/Makefile.strucpp) uses C++17, `STRUCPP_THREADED`, `-fno-gnu-unique`, and optional retain API probing. Required exported symbols, configuration/task names, debug symbol layout and the STruCpp runtime library license exception must be verified against actual generated artifacts before accepting a package.

The native upload route stops the current PLC before extraction. Its compile orchestration later invokes `compile-clean.sh`, which removes previous `build/libplc_*.so` files and renames the new library. Therefore native upload is not a separate staging/activation operation and does not provide the required recovery guarantee. The product adapter must keep real-device upload disabled. A separate authenticated coordinator must isolate candidate builds, verify their identity/ABI, preserve an active version and atomically activate only after explicit stopped-state and recovery checks. No such activation or networking endpoint is enabled by this install route.

`candidate-store.py` supplies only the offline storage boundary for that future sidecar. Given a package path and an independently approved SHA256 (`python3 candidate-store.py package.zip --sha256 HASH`), it stores immutable bytes in a separate private `candidates/HASH` directory and records `StagedArchiveUnverified`, `packageAbiVerified=false`, and `activationSupported=false`. It neither extracts nor executes the archive, invokes the compiler, contacts a device, or writes active Runtime files. Its tests prove wrong hashes are refused before candidate creation and staging preserves an existing active artifact. HTTP authentication, candidate compilation, ABI validation and transactional activation remain deferred until the actual package profile is verified.

Local isolation tests use exact pinned source fixtures and verify safe-mode startup; they compile the patched Python text without importing or starting the Runtime. Shell syntax was checked with `bash -n`. Actual Linux native daemon build, dependency resolution, private account initialization and normal-certificate-validation HTTPS reads passed. Resolved dependency versions and native linkage evidence were copied to `artifacts/device`.

Discover the installation tests with `python -B -m unittest discover -s linux/runtime-install -p 'test_*.py'`. On Windows the POSIX file-permission test is skipped; it must also run on Linux. The launcher gate accepts a checksum-bound committed library or an explicitly adopted empty baseline reserving the exact `source/build/libplc_stworkbench.so` pathname. Pending prepared/swapped transactions, unknown libraries and inconsistent identity block startup. The private deployment coordinator is installed separately in `/home/a/st-workbench-deployment`; its initial actual status was `stopped`, with no active identity or transaction. Its staging/compile and transaction verification are separate from the offline candidate-store helper described above.

Independent MIT compatibility headers live in `tools/runtime-compat/include`. Their original upstream implementations were not read or copied. Actual device GCC14.2 tests passed six C++14/C++17 plain/threaded/exception-disabled variants, including detached forced-value snapshots, noncopyable global identity and four threads executing80000 protected increments. These results cover the supplied interface contract; the full newly packaged candidate still requires independent compilation and ABI probing before activation.

`prepare-counter-candidate.py` isolates the one reviewed smoke package (SHA256 `d2f714ecdb07a305579a83b4b7ce10adf6741cfeb24ce91e18f3897471c53727`) in `candidates/HASH/work`, copies only the necessary pinned source/build scripts and normalizes shell scripts to LF. `candidate-probe.cpp` uses the Runtime's own `strucpp_abi.hpp` mirror, loads the resulting library with `RTLD_NOW`, checks required exports, MD5, configuration/resource/task descriptors, and debug-table reads. The actual compiled counter advanced from0 to10 over ten calls in that independent test process. Native symbol checks confirmed required exports and absence of GNU_UNIQUE symbols. This verifies the hardware-free smoke fixture's ABI, not generic package safety, Runtime scheduling, activation/recovery, online network debugging or axis motion. The independent Runtime's active build directory retained no program library during these tests.
