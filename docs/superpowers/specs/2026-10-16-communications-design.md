# PLC 底层通信设计

状态：用户于 2026-10-16 确认“通信先做主站/客户端，其他范围照上面”。据此实施第一期：Modbus 主站与 TCP 客户端，串口点对点收发保留；从站/服务端不在本期。与控制算法库分成两个可独立验收的实现单元。沿用本目录、自研代码可商用、原界面布局和工程逻辑兼容的要求。“x点对点”按串口自由协议点对点收发理解。

## 运行位置与方案

推荐 Linux PLC 端执行真实通信；ST 每个扫描周期只提交有界请求、获取反馈，独立工作线程负责串口、网络、超时和组帧。Windows 工程站负责组态、编程和诊断，MCP 复用工程配置及库接口。

备选一是在上位机轮询并转发数据：部署简单，但 PLC 通信依赖电脑常开，不作为推荐主方案。备选二是在 PLC 扫描中直接调用阻塞串口/Socket：代码短，但响应等待会拖慢周期，不采用。后台通信不代表网络具有硬实时保证。

## 协议和角色

| 通道 | 范围 |
|---|---|
| Modbus TCP | 客户端/主站，读取远端四区及写入可写区 |
| Modbus RTU | RS485/RS232 主站，CRC16、帧间隔、从站地址、广播写语义 |
| 串口自由协议 | RS485/RS232 二进制或文本收发，固定长度、分隔符、空闲间隔组帧 |
| 通用 TCP | 客户端，有界连接、发送、接收；原始流和可配置长度前缀/分隔符组帧 |

Modbus 常用功能码提供 01/02/03/04、05/06、0F/10、16/17；未支持的功能码返回明确异常。四区分别为线圈、离散输入、保持寄存器、输入寄存器。协议地址统一为零基地址，界面可辅助显示 40001 等文档编号，避免混用。单次读写长度按功能码规范校验，跨区/越界请求拒绝；广播写不等待响应，不冒充从站已确认。

寄存器线序按协议处理；跨寄存器的 INT32/REAL 等编码显式配置字序，不猜测设备格式。TCP 处理拆包、粘包、事务号、Unit ID、长度及异常响应；串口处理 CRC、截断、地址不匹配和过期响应。写请求发送后结果不明时返回 Unknown，不自动重发；读请求也不自动重试。

通用 TCP 是字节流，不承诺一次发送对应一次接收。文本编码、终止符及长度前缀规则必须明确，二进制使用 BYTE 数组和实际长度，不能依赖 STRING 保存任意零字节。通用 TCP 不等于 UDP、HTTP 或任意厂商协议已实现。

## 串口及资源归属

串口配置包含设备路径、波特率、数据位、校验位、停止位、RS232/RS485 模式、收发超时及组帧参数。485 增加驱动支持的自动方向/RTS 控制及切换延时，必须报告内核/转换器是否支持；不默默退化为另一物理模式。

同一物理串口由一个通道独占，不能同时开启 Modbus 和自由协议。每个 RTU 主站总线串行调度事务；TCP 客户端连接数量有明确上限。设备侧权限、端口占用、断线、队列满、超时和协议错误均返回可诊断状态。

协议代码自研，使用 Linux POSIX 串口/Socket 能力和有界事件循环；不将第三方主站/商用 SDK 链接进新组件。Modbus 定义以官方协议资料核对，参考 https://www.modbus.org/modbus-specifications；不复制规范全文进产品，也不宣称官方认证。RTU 物理时序和 USB 转换器延迟须现场验证，软件单元测试不代替真实电气验证。

## ST 接口与运行契约

新增通信库，WB_MB_REQUEST、WB_COMM_CLOSE、WB_SERIAL_SEND、WB_SERIAL_RECEIVE、WB_TCP_CONNECT、WB_TCP_SEND、WB_TCP_RECEIVE、WB_TCP_CLOSE。最终接口在实现计划中固定，资源库中的声明和调用必须来自同一权威定义。

组态生成固定 COMM_REF 通道常量，ST 通过通道引用调用功能块，不在扫描中临时打开任意路径。命令型功能块采用 Execute 上升沿、Busy、Done、Error、ErrorID 和 RequestId；接收也采用 Execute 上升沿及完成数据快照。一次提交只执行一次，Busy 期间拒绝冲突请求。Done 代表该操作已验证完成；发送成功、远端确认和远端实际动作完成必须区分。

固定缓冲容量、最大通道数、单通道在途事务数及每扫描处理量在实现计划中明确。扫描钩子不进行系统调用、动态分配、文件读写或网络等待。后台与生成程序采用独立有界收发队列，响应匹配通道、会话和请求身份；重启后旧响应不能落到新请求。

网络线程不直接改写任意 PLC 内存，结果在扫描边界通过显式有界缓冲交换。PLC 停止或程序切换后，通道不继续执行旧程序写入，待处理操作明确中止或未知，后台释放资源。

## 工程站、打包和 MCP

在原硬件/网络页面内增加通信通道配置及诊断，不重排已有页面。串口属性在硬件侧、网络端点在网络侧编辑，引用同一配置对象。工程模型新增可选通信配置；老工程省略字段，保持既有身份兼容。

通信配置进入不可变构建快照和候选身份，随源码、原生桥及通信库一起打包。编译器适配必须支持通信与轴控、路径和算法库组合，不能因新增通信覆盖现有扫描钩子。设备安装和运行前检查路径权限/端口/清单身份，缺少后端不能显示为就绪。

右侧资源库提供可拖入并可编译的调用及声明。MCP 提供通信组态、接口目录和只读状态；设备写入仍通过已保存、已构建的 PLC 程序及现有设备权限流程，不新增任意主机/串口的隐式代理。

## 验收和交付

先写协议编解码、角色状态机和错误测试，再通过本机 Socket 与 Linux 伪终端验证真实底层收发；注入拆包/粘包、坏 CRC、异常帧、断连、超时、过期回包、繁忙和关闭。使用独立协议对端交叉验证主从互通，避免只证明自家编码与解码相互匹配。

真实 ST 编译、Linux 原生候选编译和扫描时序验证必须通过，并覆盖通信与轴控同时使用、通道映射更新、程序停止和重载。实物 RS485/RS232 接线、方向控制及现场设备读写另外记录，未联调不宣称已接通。
