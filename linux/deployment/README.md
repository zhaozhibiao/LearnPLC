# Private Runtime deployment coordinator

This Python standard-library CLI stages, compiles, explicitly activates, starts, and stops local candidates for the private OpenPLC Runtime v4.3.0 instance. It never calls the native upload endpoint. Copy this directory to `/home/a/st-workbench-deployment/` and copy `config.example.json` to `config.json` only after verifying the private safe-mode service and Runtime source installation. The configuration deliberately permits only the exact private source/prefix, user unit `stworkbench-openplc.service`, and local HTTPS Runtime. Store device login credentials in the indicated mode0600 file; no password or token enters a project, request log, or output.

Call `python3 coordinator.py` with one JSON request on stdin. Every request needs an identifier matching `[A-Za-z0-9_-]{1,80}`. Responses are one JSON object with matching `request_id`, `success`, and `state`. The .NET RemoteDeploymentClient invokes this fixed path through SSH with strict known-host verification and batch authentication. No operation is automatically retried: after SSH timeout, query status and the journal before deciding another action.

Actions:

- `stage`: supply `build_hash`, `package_sha256`, and either `package_base64` or a package path already copied to the device. Validates a 32MB archive limit, 128MB expanded limit, 1024-member limit, path/symlink/member-type restrictions, complete inventory SHA256s, compiler/Runtime pins, and symbol identity before extraction under `.versions/<BuildHash>/core/generated`. It does not touch the active library or start/stop Runtime.
- `compile`: supply `build_hash`. Revalidates the staged files, copies only pinned compile inputs from the installed Runtime source, and runs the original Makefile in the isolated version workspace with one compiler job. Canonical LF source hashes avoid Windows-checkout CRLF failures. Requires successful exit, nonempty `new_libplc.so`, and all required defined exports from `nm -D`. Logs are bounded to1MB and compilation times out after300seconds. Result includes the compiled library checksum and request identity. No active library is replaced.
- `adopt-baseline`: explicit initialization requires exact stopped Runtime and exactly one regular existing library. Stores its actual pathname and checksum as baseline identity.
- `adopt-empty-baseline`: explicit first initialization requires zero matching program libraries and either exact EMPTY or exact STOPPED from the verified private safe-mode instance. Establishes null active identity and canonical `libplc_stworkbench.so` target. INIT, UNKNOWN, RUNNING, ERROR, and TRANSITIONING are refused. An arbitrary STOPPED Runtime is not automatically treated as empty; private safe-mode installation verification is required.
- `activate`: supply compiled `build_hash` and `expected_active_build_hash` (null only for an explicitly adopted empty baseline). Requires actual STOPPED or the explicit EMPTY/no-library baseline, validates baseline and candidate checksums, journals and saves a baseline backup. It stops the exact private user service and confirms it inactive before atomically replacing the same active filename; matching multiple `libplc_*` filenames are refused because the native loader chooses the first. It commits active identity and journal, then restores the service in safe mode and confirms STOPPED without sending START. **Activation temporarily disconnects online debugging; debugging returns after service restart. The PLC remains stopped until an explicit Start action.**
- `start` / `stop`: separate explicit actions bound to `expected_active_build_hash`. Send one authenticated REST control request through the Runtime webserver, then require the exact resulting state. Stop acknowledgement is not treated as completed teardown.
- `status`: returns disk identity and journal even while Runtime is unavailable, clearly setting runtime_confirmed=false; when reachable it also returns actual Runtime state, active identity with programMD5/symbol/hardware hashes, journal, and optional candidate result when `build_hash` is supplied.
- `recover`: explicit recovery of an interrupted prepared/swapped journal; stops the private service, restores the recorded baseline after checking backup checksum, records rollback, then restores safe-mode service. It never starts the PLC.

## Protocol and startup gate

Scoped transfer adds `program-export`, `program-debug-map`, `hardware-export` and `hardware-stage`.
Program exports read only the verified active library/version, its successful compilation record and checksum-covered inventory. The source archive preserves original ST and full project object metadata; a legacy version without the archive reports that ST cannot be restored. Debug-map export remains available independently of source archives and includes both parsed `debug_map` and exact UTF-8 `debug_map_json`, whose SHA256 is `symbol_table_hash`.

Hardware export requires a recorded applied build, matching native loaded topology and advancing feedback; configured axes additionally require the loaded axis-manifest digest. It returns the corresponding saved engineering `configuration` and actual `applied` identity, never an offline candidate. All exports are read-only and do not stop the PLC. Source archives are bounded to 16 MiB and program transfer payloads to 20 MiB.

`hardware-stage` accepts only inventory-covered `hardware-only` bundles with topology, machine, IO, saved configuration and axis manifest. These bundles do not require ST or target C++ compilation and cannot enter program compile/activate. `hardware-apply` uses the existing restricted hardware broker, applies configured axes even if the ST does not use MC blocks, and leaves the PLC stopped. IO-only bundles need no axis bridge. Start retains the active program's hardware and logical-axis compatibility gates.

Generic EtherCAT downloads support read-only `configuration-plan`; the current desktop refuses program download on a mismatch and never applies hardware implicitly. Separate `hardware-stage` / `hardware-apply` use a hardware-only bundle without ST compilation. `program-export` and `program-debug-map` read the verified active version; `hardware-export` reads verified applied configuration. The independent engineering HTTPS service provides authenticated transport. See [scoped transfer](../../docs/scoped-engineering-transfer.md). Legacy `configuration-apply` remains an explicit compatibility API, never part of current program download. Status and Start verify the active program's axis manifest and hardware identity before allowing an old program to run.

Pinned source `core/src/plc_app/unix_socket.c` accepts one persistent AF_UNIX client at a time. Its ASCII newline protocol includes STATUS, STOP and START. STOP:OK precedes asynchronous teardown; only STATUS:STOPPED confirms stopped. The webserver RuntimeManager owns this persistent native socket, so production control goes through authenticated local HTTPS with ordinary CA and hostname validation. The official `/api/status` returns strings such as `STATUS:STOPPED`, not simply `STOPPED`. Portable fake-daemon tests verify the exact native encoding through a local test socket; production configuration requires REST.

`core/src/plc_app/plcapp_manager.c` scans build/ for the first filename beginning `libplc_` and containing `.so`; consequently old backups are stored outside that directory and active swaps reuse one fixed pathname. Required exports come from `core/src/plc_app/image_tables.cpp` symbol resolution. Runtime-owned shim and compile inputs are pinned in `runtime-profile.json` to commit `a9e38d901fb87deb5a8cf778b52639b9387834d0`.

The private service launcher must reject `transaction.json` states other than committed or rolled-back BEFORE launching the webserver/native daemon; it must verify active.json library path/checksum and refuse unknown or extra program libraries. The coordinator deliberately leaves unfinished journals blocking normal changes until explicit recovery. Native startup must retain `--safe-mode`; no restart or recovered transaction may issue START. Systemd KillMode must be control-group, so stopping the private service also terminates its daemon and removes competing Runtime control while the active file changes. Do not share this private user service with external deployment/control clients.

## Validation

Run `python -m unittest discover -s linux/deployment -p test_coordinator.py` and `dotnet run --project tests/StWorkbench.Deployment.Tests -c Release`. Local tests use an IO-free fake daemon and disposable library bytes; they do not validate real device movement or production safety. Real Linux compilation/ABI validation and activation/start/stop evidence must be reported separately. Local candidate packaging does not clear unresolved third-party licensing for a distributed commercial product.
